아직 릴리스가 나오지 않았으므로 서버는 소스에서 빌드합니다. 서버는 암호문만 저장하고 미디어를
절대 디코딩하지 않습니다. 모든 처리와 암호화는 클라이언트가 수행합니다.

<a id="what-you-need"></a>

## 필요한 것

- **PostgreSQL 18**: 영구 색인(계정, 에셋, 할당량)과 서버의 만료되는 상태(로그인 세션, 업로드
  세션, 요청 횟수 카운터)를 담습니다. 서버가 사용하는 유일한 데이터베이스이며, 내구성 설정을
  그대로 유지한 채 실행해야 합니다([](#postgresql)).
- `fsync`를 준수하고 파일 잠금을 공유하는 **하나의 POSIX 파일 시스템** 위의 **블롭
  디렉터리**(`BLOB_ROOT`). 블롭과 함께 `ledger/` 아래에 각 소유자의 서명된 원장을 보관하며, 이
  원장으로 색인을 다시 구축할 수 있습니다([](#블롭-디렉터리)).
- 서버 앞단에서 TLS를 종료하고 압축을 손대지 않고 그대로 통과시키는 **리버스
  프록시**([](#리버스-프록시)).
- NTP로 유지되는, 호스트의 **동기화된 시계**([](#시계)).

### PostgreSQL

서버는 행이 커밋되면 쓰기에 응답하므로, PostgreSQL이 확인 응답한 뒤 잃어버린 커밋은 취소된
세션을 되살리거나 2단계 인증 코드를 두 번 받아들이게 만들 수 있습니다. 다음을 유지하세요.

- 기본값인 `fsync = on`과 `full_page_writes = on`
- `synchronous_commit`은 `on`, `local`, `remote_write`, `remote_apply` 중 하나로, 절대 `off`로
  두지 않기
- 데이터 디렉터리는 플러시를 준수하는 저장 장치에 두기. 정전 보호 기능이 없는 디스크 쓰기
  캐시나, 호스트가 플러시를 무시하는 가상 디스크는 정전 시 확인 응답한 커밋을
  잃습니다([](/design/filesystem/server/)).

PostgreSQL은 `BLOB_ROOT`와 다른 파일 시스템, 디스크, 호스트에 있어도 됩니다.

<a id="blob-directory"></a>

### 블롭 디렉터리

`BLOB_ROOT`는 파일 시스템과의 계약이며([](/design/filesystem/server/#blob-root-filesystem-contract)),
구조는 [](/design/filesystem/server/#blob-store-layout)와 같습니다.

- **하나의 파일 시스템.** 최종 확정은 원자적 이름 변경이므로, `incoming/`을 포함한 전체 트리는
  여러 볼륨, 데이터세트, Kubernetes PersistentVolume에 걸칠 수 없습니다.
- 서버가 쓰기를 확인 응답하기 전에 파일과 디렉터리 모두에서 **`fsync`가 준수되어야 합니다**.
- 트리에 쓰는 모든 프로세스가 **파일 잠금을 공유해야 합니다**. `serve`와 `purge --apply`는 내용을
  추가하기 전에 각 소유자의 `ledger/<owner>/.lock`을
  잠급니다([](/design/filesystem/server/#concurrent-appenders)).
- **블롭 디렉터리 하나에 `serve` 하나.** 업로드 청크와 최종 확정은 서비스 중인 프로세스 안에서
  점유되므로([](/design/transfer/upload/)), 같은 호스트든 서로 다른 두 호스트든 한 트리에서 두
  개의 `serve` 프로세스를 실행하는 것은 지원되지 않습니다. `gc`, `purge`, `scrub`은 함께 실행할
  수 있지만, `rebuild --apply`는 `serve`를 멈춘 상태에서 실행해야 합니다([](#유지-관리)).

지원됨:

- 로컬 또는 블록 저장 장치(디스크, RAID, LVM, iSCSI, 클라우드 블록 볼륨) 위의 ext4, XFS, btrfs
- `sync=standard`(기본값) 또는 `sync=always`로 설정한 ZFS
- `sync`로 내보낸 NFSv4, 또는 잠금 관리자를 사용하는 NFSv3
- 위 중 하나를 기반으로 하는 Kubernetes PersistentVolume 또는 컨테이너 볼륨

지원되지 않음:

- 쓰기 배리어를 끈 마운트, 또는 호스트가 플러시를 무시하는 가상 디스크
- 쓰지 않고도 `fsync`를 확인 응답하는 `sync=disabled` 설정의 ZFS
- NFS 서버가 저장하지 않은 쓰기를 확인 응답하는 `async` 내보내기 NFS, 또는 잠금을 한 호스트에만
  유지하는 `nolock`, `local_lock=flock`, `local_lock=all` 마운트 NFS
- SMB/CIFS 공유
- FUSE 파일 시스템(sshfs, rclone mount, s3fs, gcsfuse)과 모든 객체 저장소 마운트
- 하나의 트리를 여러 디스크에 분산하는 풀링 및 유니언 파일 시스템(mergerfs, `/mnt/user` 아래의
  Unraid 사용자 공유). 구성 디스크 간 이름 변경은 원자적 이름 변경이 아니라 복사입니다.
- 컨테이너 자체의 쓰기 가능 레이어, 그리고 컨테이너 VM에 바인드 마운트한 macOS 또는 Windows
  호스트 디렉터리. VM 안의 볼륨을 사용하세요.

Linux에서 NFS 위의 `flock`은 바이트 범위 잠금으로 에뮬레이션되며, 잠금 관리자가 이를 호스트
간에 공유합니다. 잠금이 비활성화되면 서로 다른 호스트의 `serve`와 `purge --apply`가 원장에
추가하는 내용이 뒤섞일 수 있습니다.

- **하드웨어를 신뢰하기 전에 정전 훈련을 하세요.** `serve`는 부팅 시 파일 시스템 유형, 원자적
  이름 변경, 잠금 공유를 확인하지만, 실제로 하지 않은 플러시를 확인 응답하는 디스크, 컨트롤러,
  하이퍼바이저는 어떤 소프트웨어 검사로도 알아낼 수 없습니다. 배포할 하드웨어에서 업로드 도중
  전원을 차단한 뒤(정상 종료가 아닌), 다시 부팅하고 `capsule-server scrub --deep`을 실행하세요.
  서버가 확인 응답한 모든 업로드가 온전해야
  합니다([](/design/filesystem/server/#blob-root-filesystem-contract)).
- **여유 공간을 남겨 두세요.** 블롭 루트는 볼륨의 2%와 4 GiB 중 큰 값을 기본 여유 공간 예비분으로
  유지합니다. 이보다 적어지면 새 업로드는 `507`로 거부되지만, 이미 서버에 올라오고 있는 업로드는
  완료되고 삭제도 계속 작동합니다([](/design/quota/#enforcement-points)). 예비분은 예정된
  기능으로 아직 구현되지 않았으며, 구현되기 전까지는 디스크가 가득 차면 모든 쓰기가 거부됩니다.
- **격리 영역은 신중하게 정리하세요.** `quarantine/`은 재해시에 실패했거나 읽을 수 없었던 블롭을
  삭제할 때까지 보관하며, 그 뒤에 복구된 블롭은 제외합니다. 예정된
  `capsule-server quarantine prune`은 삭제하기 전에 목록을 보여 주며 `--apply` 없이는 아무것도
  삭제하지 않습니다([](/design/filesystem/server/#quarantine-retention)). `scrub`이 격리 영역의
  크기를 보고하므로 거기서 지켜보세요.

<a id="reverse-proxy"></a>

### 리버스 프록시

TLS는 서버가 아니라 항상 프록시에서 종료됩니다([](/design/networking/#transport-security)).
서버는 평문 HTTP로 수신하며 루프백, 사설 네트워크, 파드 네트워크를 통해 프록시에서만 접근할 수
있어야 합니다. 프록시를 다음과 같이 구성하세요.

- 가장 큰 업로드 청크인 16 MiB 이상의 요청 본문을 받아들이기
- 요청 본문을 버퍼링하지 말고 서버로 스트리밍하기
- TLS 조기 데이터(0-RTT)를 비활성화하거나, 서버가 쓰기를 거부할 수 있도록 `Early-Data: 1`
  헤더와 함께 전달하기
- 느리지만 꾸준한 청크가 끊기지 않도록, 요청 본문에 전체 소요 시간 제한을 두지 말고 유휴
  시간 제한은 서버의 정체 한도보다 길게 두기
- **압축을 그대로 통과시키기.** 어떤 응답을 압축할지는 서버가 정하며, 서버는
  `application/octet-stream`을 절대 압축하지 않습니다([](/design/networking/#compression)).
  프록시는 Capsule의 업스트림 응답을 서버가 보낸 그대로 전달합니다. 프록시는 응답을 gzip이나
  다른 방식으로 압축해서는 안 되며(MUST NOT), 응답의 압축을 풀거나 `Content-Encoding`을 추가,
  변경, 제거해서도 안 되고(MUST NOT), 클라이언트의 `Accept-Encoding`을 변경 없이
  전달해야 합니다(MUST). nginx에서는 Capsule 사이트에 `gzip off;`를 유지해 배포판의
  `nginx.conf`에서 상속된 `gzip on;`을 덮어쓰세요. Caddy에서는 `encode` 지시어를 추가하지 말고,
  Traefik에서는 `compress` 미들웨어를 붙이지 마세요.

프록시의 클라이언트 쪽 HTTP/2와 HTTP/3는 선택 사항이며, 클라이언트는 HTTP/1.1로 대체합니다.
커널 TLS(kTLS)와 NIC TLS 오프로드를 원한다면 프록시에서 설정합니다(nginx에서는
`sendfile on;`과 함께 `ssl_conf_command Options KTLS;`). 서버 자체의 TLS 스택은 서버가 직접 여는
연결, 즉 OpenID Connect 공급자와 페더레이션 피어로의 연결에만 사용됩니다. 이 연결은 호스트의
인증서 저장소가 아니라, 번들로 포함된 Mozilla 루트 인증서와 `OIDC_CA_BUNDLE`을 신뢰합니다.

<a id="clock"></a>

### 시계

서버는 자신의 시계로 시간을 판단하며, 여러 규칙이 그 시계가 정확하다는 데 의존합니다. 호스트에서
NTP(chrony 또는 systemd-timesyncd)로 시계를 동기화하세요. 컨테이너는 호스트의 시계를 읽으므로
호스트를 동기화하세요. 오차는 1초 이내로 유지해야 하며(SHOULD), 30초를 넘어서는
안 됩니다(MUST). 이 한도를 넘으면:

| 오차        | 무엇이 깨지는가                                                                                                                                                       |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 30초 초과   | 2단계 인증 코드가 실패하기 시작합니다. 코드는 서버 시계 기준 30초 단계 하나 안에서만 받아들여집니다([](/design/authentication/))                                      |
| 5분 초과    | 페더레이션이 양방향으로 멈춥니다. 피어는 이 서버의 서명된 요청, 힌트, 보고를 거부하고, 이 서버도 피어의 것을 거부합니다([](/design/federation/))                      |
| 시계가 빠름 | 휴지통이 보존 기간이 끝나기 전에 영구 삭제되고, 제때 한 복원이 거부됩니다([](/design/organization/#retention-window)). 세션, 공유 링크, 업로드 세션이 일찍 만료됩니다 |
| 시계가 느림 | 만료된 세션, 공유 링크, 카운터가 설정보다 오래 유효합니다                                                                                                             |
| 심각한 오차 | 클라이언트가 `received_at`이 비현실적인 보관 영수증을 거부합니다([](/design/transfer/durability/))                                                                    |

시계가 동기화된 뒤에만 `serve`를 시작하세요. systemd에서는 `chrony-wait.service` 또는
`systemd-time-wait-sync.service`를 활성화하고 `time-sync.target` 뒤에 실행되도록 순서를
지정하세요. 스냅샷에서 복원된 가상 머신은 스냅샷 당시의 시계로 재개되므로, `serve`가 시작되기
전에 NTP가 시계를 맞추도록 하세요. 서버는 아직 시계 오차를 스스로 감지하거나 보고하지 않습니다.

<a id="hardware"></a>

## 하드웨어

이 수치는 서버와 PostgreSQL을 함께 실행하는 노드 하나를 기준으로 합니다. 벤치마크가 아니라 서버가
하는 일에서 도출한 규모 산정 지침입니다.

서버가 하는 일은 가벼우므로, 하드웨어 예산의 대부분은 **저장 장치**에 써야 합니다. 서버는 각
청크가 도착할 때 SHA-256으로 해시하고, 최종 확정 시와 `scrub --deep` 중에 다시 해시합니다. 최종
확정 시 클라이언트의 하이브리드 서명(Ed25519와 ML-DSA-65)을 검증하고, 영수증도 같은 방식으로
서명하며, 비밀번호 로그인마다 Argon2id를 한 번 실행합니다(각각 약 19 MiB). 미디어를 디코딩,
크기 조정, 트랜스코딩하지 않고, 암호화나 복호화도 하지 않으며, TLS는 리버스 프록시에 맡깁니다.
업로드 본문은 청크 하나를 넘어서 버퍼링되지 않으므로 메모리 사용량은 파일 크기에 따라 늘지
않습니다.

|                      | 최소                                                | 권장                                                                                                                         |
| -------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **CPU**              | 2코어, x86_64 또는 arm64                            | 4코어. SHA-2 명령어(x86_64의 SHA-NI, Armv8 암호화 확장)가 해시 속도를 높입니다                                               |
| **RAM**              | 2 GB                                                | 4~8 GB. 대형 라이브러리에서는 메모리가 많을수록 PostgreSQL 캐시에 도움이 되지만, 저장 장치에 먼저 투자하는 편이 효과적입니다 |
| **시스템 저장 장치** | SSD, 여유 공간 10 GB                                | PostgreSQL용 SSD 또는 NVMe                                                                                                   |
| **블롭 저장 장치**   | 라이브러리 크기에 진행 중인 업로드를 위한 공간 추가 | 몇 년간의 증가를 감안한 이중화 디스크(미러, RAID, ZFS). 회전식 디스크도 괜찮습니다                                           |
| **네트워크**         | 업스트림 10 Mbit/s                                  | LAN에서는 기가비트, 기기가 외부에서 동기화한다면 업스트림 50 Mbit/s 이상                                                     |
| **전원**             | —                                                   | 정전이 PostgreSQL의 쓰기 도중에 끼어들지 않도록 UPS                                                                          |

- **`BLOB_ROOT`는 하나의 파일 시스템에 둡니다.** `incoming/`을 포함한 전체 트리가 하나의 파일
  시스템이어야 하므로, SSD와 디스크 어레이 또는 두 ZFS 데이터세트에 나눠 둘 수 없습니다. 전부
  어레이에 두세요.
- **서버가 쓰지 않는 메모리는 PostgreSQL에 주세요.** 인증된 모든 요청은 PostgreSQL에서 세션을
  읽고 모든 업로드 청크는 그곳에 범위를 기록하므로, PostgreSQL 캐시는 라이브러리 색인뿐 아니라
  요청 경로에도 쓰입니다. 세션, 업로드 세션, 카운터는 작으며 서버가 만료되면 삭제합니다.
- **원격 기기에서는 업스트림 대역폭이 한계입니다.** 네트워크 밖의 휴대폰은 회선의 _다운로드_
  속도로 업로드하지만, 미리보기나 원본을 가져갈 때마다 데이터는 _업스트림_ 속도로 나갑니다.
  청크는 오래 걸린다는 이유로는 끊기지 않고 도착이 멈출 때만 끊기며, 클라이언트는 측정한 속도에서
  짧은 목표 시간 안에 끝나도록 청크 크기를 정하므로 느린 회선도 자기 속도대로 업로드합니다. 서버의
  정체 한도를 프록시의 유휴 시간 제한보다 짧게 두어, 프록시가 끊기 전에 서버가 정체된 청크에
  응답하게 하세요.
- **디스크 크기는 파생 파일이 아니라 원본 기준으로 정하세요.** RAW 파일과 동영상으로 이루어진
  라이브러리에서 파생 파일은 작은 비율에 불과합니다. 서버는 각 블롭을 클라이언트가 암호화한
  그대로 한 번만 보관합니다.
- **사용자가 늘면 연산이 아니라 대역폭이 늘어납니다.** 검색, 썸네일, 정리는 클라이언트에서
  실행됩니다. 둘러보는 사람이 많아지면 전송되는 바이트는 늘지만 CPU와 RAM은 거의 늘지 않습니다.

`capsule-server/compose.yaml`은 로컬 사용에 맞는 설정으로 Postgres를 실행합니다
(`mise run serve-deps`). 그 자격 증명은 개발 전용입니다.

<a id="build"></a>

## 빌드

```sh
cargo build --release -p capsule-server -p capsule-server-migration
```

바이너리는 glibc에 링크되며 그 밖에 설치할 것은 없습니다. 쓰기 가능한 경로가 `BLOB_ROOT`뿐인
비특권 사용자로 실행하세요. 아래 컨테이너 이미지가 강제하는 것과 같은 구성입니다.

<a id="container-image"></a>

## 컨테이너 이미지

:::caution
아직 게시된 이미지가 없으며, `/livez`와 `/readyz` 경로와 `healthcheck` 하위 명령도 아직 구현되지
않았습니다. 이 섹션은 이미지가 따르는 계약입니다.
:::

- **베이스:** 다이제스트로 고정한 `gcr.io/distroless/cc-debian12:nonroot`. glibc, GCC 런타임,
  CA 인증서, 시간대 데이터를 포함하며 셸과 패키지 관리자는 없습니다.
- **아키텍처:** `linux/amd64`와 `linux/arm64`용 멀티 아키텍처 이미지 하나이며, 각각 해당 glibc
  타깃에서 네이티브로 빌드됩니다. 빌드는 특정 CPU에 맞춰 조정되지 않으며, 해시는 실행 시점에
  SHA-NI 또는 Armv8 암호화 확장을 선택합니다.
- **내용:** 같은 빌드에서 나온 `capsule-server`(엔트리포인트, 기본값은 `serve`)와
  `capsule-server-migration`.
- **사용자:** 루트가 아닌 UID 및 GID 65532. 컨테이너에는 Linux 기능(capabilities)이 필요 없으니
  모두 제거하고 `no-new-privileges`를 설정하세요.
- **읽기 전용 루트 파일 시스템.** 서버는 `BLOB_ROOT` 아래에만 쓰므로, 블롭 디렉터리를 UID
  65532가 소유한 유일한 쓰기 가능 볼륨으로 마운트하고 루트는 읽기 전용으로 마운트하세요.
- **리스너:** 컨테이너 안에서는 `SERVER_HOST=0.0.0.0`(또는 `::`)을 설정하세요. 기본 포트는
  3000입니다. 리버스 프록시에만 공개하세요([](#리버스-프록시)).
- **로그**는 stderr로 출력됩니다. 로그 수집기를 쓴다면 `LOG_FORMAT=json`을 설정하세요.
- **중지:** `serve`는 `SIGTERM`을 받으면 정상적으로 종료합니다. 중지로 끊긴 업로드는 서버에
  커밋된 범위부터 다시 이어집니다.
- **레플리카 하나.** 블롭 디렉터리당 정확히 하나의 `serve`를 실행하세요([](#블롭-디렉터리)).
  Kubernetes에서는 `Recreate` 업데이트 전략으로 레플리카 하나를 사용하세요. 롤링 업데이트는 이전
  서버가 아직 서비스하는 동안 새 서버를 시작합니다.
- **마이그레이션**은 `serve`가 시작되기 전에 같은 이미지 태그에서 Job, init 컨테이너,
  `ExecStartPre=` 중 하나로 실행합니다: `capsule-server-migration up`([](#마이그레이션-후-시작)).
- **유지 관리** 명령은 같은 이미지에서 같은 사용자로, 같은 볼륨에 대해 CronJob이나 타이머로
  실행합니다([](#유지-관리)).
- **상태 확인:** `/livez`는 프로세스가 서비스하는 동안 `GET`에 응답하며 그 밖에는 아무것도
  확인하지 않으므로 활성 프로브(liveness probe)에 씁니다. `/readyz`는 PostgreSQL이 응답하고,
  스키마가 바이너리와 일치하며, `BLOB_ROOT`에 쓸 수 있는 동안에만 응답하므로 준비 프로브(readiness
  probe)에 씁니다. 둘 다 `/v1` 밖에 있어 프로브가 프로토콜 버전에 의존하지 않으며, 둘 다
  프록시를 통해 접근할 수 있을 필요는 없습니다. 이미지에는 `curl`이 없으므로 이미지 자체의 상태
  확인은 로컬 리스너의 `/livez`를 호출하는 `capsule-server healthcheck`를 실행합니다.
- **시계:** 컨테이너는 호스트의 시계를 읽으므로 호스트를 동기화하세요([](#시계)).

<a id="configure"></a>

## 구성

구성은 환경 변수로만 합니다. `capsule-server/.env.example`은 시작용 템플릿이며, 이 페이지는
운영자가 정해야 하는 변수를 다룹니다. 영구 저장 서버는 다음이 없으면 빠진 변수를 한 번에 모두
알려 주며 시작을 거부합니다(종료 코드 2).

| 변수                   | 용도                                                              |
| ---------------------- | ----------------------------------------------------------------- |
| `DATABASE_URL`         | PostgreSQL 연결                                                   |
| `BLOB_ROOT`            | 블롭 디렉터리                                                     |
| `JWT_ED25519_DER`      | 세션 토큰에 서명하는 Base64 Ed25519 키                            |
| `ATTESTATION_KEY_SEED` | 보관 영수증에 서명하는 Base64 시드. 토큰 키와 독립적이어야 합니다 |

- **무엇보다 토큰 키를 지키세요.** 데이터베이스에는 베어러 비밀이 없으므로 데이터베이스나 백업이
  유출되어도 그것만으로는 세션을 얻을 수 없습니다. 그런 유출을 모든 활성 세션의 탈취로 바꾸는
  것이 `JWT_ED25519_DER`입니다([](/design/authentication/#session-token)). 리프레시 토큰 재사용
  탐지([](/design/authentication/#token-lineage-and-reuse))는 이에 대해 도움이 되지 않습니다. 키를
  가진 사람은 토큰을 재사용하는 것이 아니라 새로 발급하기 때문입니다. 키는 데이터베이스나 그
  백업이 아닌 비밀 저장소에 보관하고, 유출이 의심되면 교체하세요. 교체하면 모든 기기가
  로그아웃됩니다.
- **2단계 인증 봉인 키가 예정되어 있습니다.** 서버는 TOTP 비밀을 토큰 키와 독립적인 전용 키로
  봉인해 저장할 예정입니다. 그러면 데이터베이스나 백업이 유출되어도 2단계 인증 정보는 노출되지
  않고, 토큰 키를 교체해도 2단계 인증이 무효화되지 않습니다([](/design/authentication/#the-second-factor)).
  이 설정은 아직 존재하지 않습니다. 도입되면 토큰 키처럼 데이터베이스와 그 백업에서 분리해
  보관하세요.
- **공개 가입에는 기본 할당량이 필요합니다**(예정). 할당량을 설정할 수 있게 되면, 비밀번호 가입이
  활성화되어 있고 기본 한도가 없을 때 `serve`는 시작을 거부합니다. 한도를 두지 않으려는 운영자는
  명시적으로 `unlimited`로 설정해야 하며, 이는 시작할 때마다 `WARN`으로
  기록됩니다([](/design/quota/#thresholds-and-states)). 현재는 모든 배포가 무제한으로
  실행됩니다.

`SYNC_CURSOR_MAC_KEY`를 설정하지 않으면 `JWT_ED25519_DER`에서 파생되므로, 명시적으로 설정하지
않는 한 토큰 키를 교체하면 발급된 동기화 커서도 무효화됩니다. 페더레이션은
`FEDERATION_ENABLED=true`와 `FEDERATION_URL`이 설정되지 않으면 꺼져 있습니다. 꺼 둔 채로 두세요.

소스별 속도 제한이 프록시가 아닌 클라이언트를 인식하도록 리버스 프록시를 지정하세요.

| 변수                   | 의미                                                                                                                  |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `TRUSTED_PROXIES`      | 쉼표로 구분한 주소와 CIDR 네트워크(`10.0.0.0/8`). `/0` 네트워크는 모든 발신자를 믿게 되므로 거부됩니다.               |
| `TRUSTED_PROXY_HOPS`   | 주소와 관계없이 서버에 가장 가까운 전달 홉을 그 수만큼 신뢰합니다.                                                    |
| `TRUSTED_PROXY_HEADER` | 서버가 읽는 단 하나의 전달 필드: `x-forwarded-for`(기본값) 또는 `forwarded`(RFC 7239). 다른 값이면 시작을 거부합니다. |

설정하지 않으면 어떤 전달 헤더도 믿지 않습니다. 이는 안전하지만, 프록시 뒤의 모든 클라이언트가
프록시의 한도를 공유하게 되므로 낯선 사람 한 명이 비밀번호를 추측하기만 해도 모두의 로그인이
느려집니다([](/design/authentication/#sign-in-limits)). 서버는 어떤 홉도 신뢰하지 않는 상태에서
전달 헤더를 보면 경고를 기록합니다. 반대 실수는 더 나쁩니다. 클라이언트 주소를 덧붙이지 않는 홉을
신뢰하면 모든 클라이언트가 자신의 속도 제한 키를 마음대로 고를 수 있게 됩니다.
`TRUSTED_PROXY_HEADER`가 지정하지 않은 필드는 누가 보내든 무시되므로, 클라이언트가 프록시가
그대로 전달하는 필드를 보내 자신의 속도 제한 키를 고를 수는 없습니다. 프록시가 덧붙이는 필드를
지정하세요. 기본값을 쓴다면, nginx가 다음 설정으로 하는 것처럼 프록시가 자신이 본 주소를
`X-Forwarded-For`에 덧붙이도록 하세요.

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

`TRUSTED_PROXY_HEADER=forwarded`는 프록시가 `Forwarded`에 자신의 요소를 덧붙이고
`X-Forwarded-For`는 쓰지 않을 때만 설정하세요.

<a id="migrate-then-start"></a>

## 마이그레이션 후 시작

`serve`는 절대 마이그레이션하지 않으며, 바이너리보다 오래된 데이터베이스 스키마를 거부합니다.
업그레이드할 때마다 먼저 마이그레이션을 실행하세요.

```sh
DATABASE_URL=… capsule-server-migration up
capsule-server serve
```

`serve`는 stderr에 로그를 남기고 stdout에 `listening on <url>`을 출력합니다. 프로덕션에서는
`--memory`를 쓰지 마세요. 블롭을 제외한 모든 것을 프로세스 메모리에 보관합니다.

<a id="maintenance"></a>

## 유지 관리

다음 일회성 명령을 예약해 두세요(cron 또는 타이머). 이 명령들은 `DATABASE_URL`과 `--blob-root`가
필요하며 기본적으로 시험 실행(dry run)으로 동작합니다.

- `capsule-server gc --apply`: 유예 기간이 지난 뒤 참조되지 않는 블롭을 회수하고, 만료된 세션,
  업로드 세션, 카운터를 삭제합니다. 저장 공간이 부족하지 않아도 정기적으로 실행하세요.
- `capsule-server purge --apply`: 보존 기간이 지난 소프트 삭제 에셋을 완전히 삭제합니다. 각
  삭제는 먼저 소유자 원장([](/design/filesystem/server/#the-owner-ledger))에 서명되어 기록되므로
  서버의 `ATTESTATION_KEY_SEED`도 필요하며, 없으면 실행을 거부합니다. 원장에 삭제를 기록하지
  못하면 0이 아닌 코드로 종료하며, 해당 에셋은 다음 실행을 위해 남겨 둡니다.
- `capsule-server scrub [--deep]`: 색인을 블롭 저장소와 대조하는 읽기 전용 무결성 검사입니다.
  **무엇이든 발견하면 0이 아닌 코드로 종료**하므로 이를 알림 조건으로
  삼으세요([](/design/filesystem/maintenance/#server-side-integrity-scrub)).

백업을 복원했거나 데이터베이스를 잃은 뒤에는 `BLOB_ROOT` 아래의 소유자 원장으로 색인을 다시
구축하세요([](/design/filesystem/server/#rebuild)). 원장의 서명을 검증할 수 있도록 호스트에
`ATTESTATION_KEY_SEED`를 설정하세요.

1. `capsule-server rebuild`는 색인을 원장과 비교합니다.
2. `serve`를 멈춘 상태에서 `capsule-server rebuild --apply`는 색인에 없는 행을 복원합니다. 색인에
   있는 행은 절대 덮어쓰지 않습니다. 끝부분을 잃은 원장은 다시 고정하며, 그 뒤 서버는 그 소유자에
   대해 다시 쓰기를 합니다.
3. 원장이 다시 쓰였다는 보고가 나오면, 조사한 뒤 `capsule-server rebuild --apply --accept-rewrites`를
   실행할 때까지 서버는 해당 소유자의 쓰기를 거부합니다.

블롭 크기를 기록하기 전에 수명 주기 작업(삭제, 복원, 메타데이터 업데이트, 파생 파일, 교체)을
적용한 서버는 해당 참조를 크기 0으로 보관합니다. `capsule-server repair-sizes`를 한 번 실행해
목록을 확인한 다음, `capsule-server repair-sizes --apply`로 블롭 저장소에서 각 크기를 채우세요.
실행 중인 `serve`와 함께 실행해도 안전하며, 복구된 각 에셋은 클라이언트에 다시 전송됩니다. 블롭이
없거나 비어 있으면 0이 아닌 코드로 종료하며 그 참조는 그대로 둡니다.

<a id="backups"></a>

## 백업

영구 상태는 PostgreSQL과 `BLOB_ROOT`(블롭과 `ledger/`)입니다. 둘 다 함께 백업하세요. 데이터베이스에는
로그인 세션과 진행 중인 업로드 세션도 있으므로, 복원해도 사용자는 로그인 상태를 유지합니다. 위의 키
변수도 비밀 저장소에 보관하세요. 이 변수는 데이터베이스에 없으며, 서버의 서명 및 증명 신원이 여기에
달려 있습니다.

데이터베이스를 먼저 백업한 다음 블롭을 백업하세요.

```sh
pg_dump --format=custom --file=capsule.dump "$DATABASE_URL"
rsync -a "$BLOB_ROOT"/ backup/blob-root/
```

`serve`는 계속 실행해도 됩니다. 블롭이 디스크에 기록되고 원장 항목이 추가된 다음에야 그 블롭을
가리키는 색인 행이 커밋되므로, 덤프 이후에 복사한 블롭에는 덤프가 참조하는 모든 블롭과, 경우에
따라 덤프가 놓친 쓰기까지 들어 있습니다. 백업이 진행되는 동안에는 `gc --apply`나 `purge --apply`를
실행하지 마세요. 둘 다 덤프가 아직 참조하는 블롭을 지울 수 있습니다.

아래의 재구축은 색인에 없는 모든 행을 추가하므로, 덤프와 블롭 복사 사이에 업로드된 에셋을
복원합니다. 덤프에 이미 있는 행은 절대 바꾸지 않으므로, 그 사이에 오래된 에셋에 대해 이루어진 삭제,
복원, 메타데이터 편집은 적용되지 않습니다. 재구축은 그런 변경이 에셋의 블롭을 바꾼 경우에만 차이가
나는 행으로 보고하며(0이 아닌 코드로 종료), 삭제나 복원은 보고되지 않습니다. 백업이 모든 변경을
담아야 한다면 두 부분을 백업하는 동안 `serve`를 멈추세요. 복원 시 차이가 나는 행이 보고되고 이전
호스트가 아직 실행 중이라면, 그 방식으로 다시 백업하세요.

<a id="restoring-onto-a-new-host"></a>

### 새 호스트로 복원하기

1. 빈 PostgreSQL을 시작하고, 이전 호스트와 같은 `JWT_ED25519_DER`와 `ATTESTATION_KEY_SEED`를
   설정하세요.
2. 데이터베이스를 복원하세요. 덤프에는 스키마와 마이그레이션 기록이 들어 있으므로
   `capsule-server-migration up`을 먼저 실행하지 마세요:
   `pg_restore --no-owner --exit-on-error --dbname "$DATABASE_URL" capsule.dump`.
3. 블롭 디렉터리를 하나의 파일 시스템 위의 `BLOB_ROOT`로 다시 복사하세요.
4. `serve`를 멈춘 상태에서 `capsule-server rebuild`를 실행하고 보고서를 읽으세요. 보고서에는
   덤프 이후에 업로드된 에셋이 나열됩니다. `capsule-server rebuild --apply`는 이 에셋들을 원래의
   시퀀스 번호로 복원하므로 클라이언트의 동기화 커서가 계속 유효합니다.
5. `capsule-server scrub --deep`을 실행하세요. 아무것도 보고하지 않아야 하며, 무엇이든 발견하면
   0이 아닌 코드로 종료합니다.
6. `serve`를 시작하세요. 세션은 데이터베이스와 함께 돌아오므로, 덤프 시점에 로그인해 있던
   클라이언트는 그 뒤 세션이 만료되지 않았다면 로그인 상태를 유지합니다. `serve`는 수신을 시작하기
   전에 `BLOB_ROOT` 아래의 임시 파일이 복원되지 않은 미완료 업로드 세션을 모두 폐기하고, 세션이
   없는 임시 파일을 모두 삭제합니다. 업로드가 폐기된 클라이언트는 그 파일을 처음부터 다시
   올립니다. 클라이언트는 멈춘 지점부터 동기화를 재개합니다.

데이터베이스를 잃었고 덤프도 없다면, 빈 데이터베이스를 마이그레이션하고 블롭 디렉터리에 대해
`capsule-server rebuild --apply`를 실행하세요. 소유자 원장에서 모든 에셋 행을 복원합니다. 계정,
게시된 기기 디렉터리, 앨범 멤버십, 공유 링크는 데이터베이스에만 있으며 재구축으로는 복원되지
않습니다.

실제 데이터를 맡기기 전에 이 과정을 미리 연습해 보세요. 예를 들어 `capsule restore`로 모든 원본이
바이트 단위로 그대로 돌아오는지 확인하세요. `capsule-e2e/tests/backup_restore_drill.rs`는 같은
단계를 컨테이너를 대상으로 실행합니다(`mise run test-rust-containers`).
