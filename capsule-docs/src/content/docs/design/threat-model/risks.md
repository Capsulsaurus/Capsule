title: Implementation Risk Register
description: Implementation faults that pass every structural check and can still lose or corrupt data, and the independent tests that must catch each one
status: draft
---

The rest of the threat model bounds what a faulty or hostile **client** can do to the server and to other clients. This page bounds a different fault: **Capsule's own code computing the wrong value consistently**. A wrong value that the client and the server compute the same way passes every server check, every custody receipt and every durability gate, because those gates check that the server holds what the client described, not that the description is right (assumption A7 of [](/design/threat-model/#assumptions)).

Each row is a fault class, not a known bug. A row is closed only when its mitigation runs in CI. A new mechanism whose correctness rests on two pieces of code agreeing MUST add a row here.

## Rules

- **One implementation per value.** The content address, the STREAM geometry, the blob header and commitment, every HKDF derivation and canonical CBOR are computed only by `capsule-core` and reached from Swift, Kotlin and the browser through UniFFI and wasm. A client MUST NOT re-implement any of them. A second implementation exists only in tests, and there it must be independent.
- **A vector generated by the code under test proves determinism, not correctness.** The guest-drop fixture (`xtask/src/drop_kat.rs`) is produced by Rust and reproduced by the same Rust compiled to wasm, so it pinned a hex-encoded passphrase proof that the server, which decodes base64 (`capsule-server/src/routes/drop.rs`), refuses for every honest guest. A fixture that both sides of a boundary consume MUST be checked by the consuming side, the server route included.
- **Agreement between client and server is not evidence.** Wherever the server re-checks a client value with the same crate, the register names an independent check.

## Required Test Infrastructure

The mitigations below name these by tag. Each is a MUST for the rows that cite it.

| Tag | Requirement |
| --- | --- |
| **T1: Independent golden vectors** | Known-answer vectors generated once by an implementation that shares no code with Capsule (Python `cryptography` for AES-256-GCM, STREAM and HKDF-SHA512, as `capsule-core/src/crypto/encryption/stream/tests.rs` already does for headerless STREAM; Python `hashlib` for SHA-256), committed as fixtures, and never regenerated by the code under test. CI runs them against every implementation that produces or consumes the value: Rust, Swift and Kotlin through their bindings, wasm, and the server's decoders. They cover the content address of whole blobs, header included; STREAM ciphertext at the first, last and a middle chunk, an empty plaintext, and a plaintext one byte either side of a chunk boundary; ranged reads at `56 + i × ciphertext_chunk`; the header bytes and the key commitment; every HKDF label with its salt layout; canonical CBOR of each signed record type; and every value one crate encodes and another decodes. |
| **T2: Differential hashing** | A property test feeds generated inputs through every production hashing path (one-shot, streaming at arbitrary read sizes, incremental during sealing, file hashing) and compares each with a SHA-256 implementation from a different crate than the one under test. The existing check compares the streaming path with `capsule-core`'s own one-shot hash (`capsule-library/src/utils/tests.rs`), which shares its `sha2` core and so cannot disagree with it. |
| **T3: Open after seal** | The sealing pass decrypts every chunk it has just produced, with the header as associated data and at the offsets a reader will use, and compares the plaintext digest with the source's before the manifest is signed. A failure aborts the write. Together with the address and the `deep` verify, this proves that the server holds bytes that open to the original, which is what verify-before-destroy ([](/design/transfer/durability/#verify-before-destroy)) needs and no server-side check can show. |
| **T4: Property and fuzz tests** | Per [](/development/testing/#rules): seeded `proptest` for every round-trip and every geometry formula; `cargo-fuzz` for every decoder and every file the client maps or parses; mutation testing on the modules a row names. |
| **T5: Fault and interleaving tests** | Faults injected through the storage and clock ports (an `fsync` returning `EIO`, a wall clock stepped forward or back) and forced interleavings of concurrent operations at named points, run in the server's conformance suites. |

| R1 | **Wrong content address.** A blob is hashed over the wrong bytes (plaintext for ciphertext, the header left out) or by a hasher that mishandles a partial final block. | Wrong input: finalize refuses, which is transient. | R5 | **Key derivation mismatch across implementations.** A different HKDF hash, label, salt layout (`file_id` as 16 raw bytes or as text) or output length. | Blobs one implementation sealed are *wrong key* on another. | R6 | **Two plaintext dedup hashes.** The Swift import hashes the original with CryptoKit over a whole in-memory buffer (`capsule-swift/Modules/ManagedStore/Sources/ImportService.swift`, `ContentHasher.swift`); Rust streams it through `hash_reader` in `capsule-core::crypto::hash` (`capsule-library/src/utils/mod.rs`). | R7 | **Serialization drift.** Canonical CBOR differs between encoders; the peering channel's JSON is `serde_json` of Rust types with byte strings as integer arrays, so a field rename or serde attribute is a wire change; a value one crate encodes another decodes differently (hex against base64 in the drop passphrase proof). | Signatures and metadata-blob hashes fail on other implementations, so valid assets are quarantined; peering stops interoperating; an honest guest is refused. | Same-language round trips accept any self-consistent encoding. | R9 | **Server clock jumps.** A restored VM snapshot or a broken time source steps the clock back or forward. | Ahead: trash is purged before its retention window ends, which is irreparable.
