<a id="collect-diagnostics"></a>

## Сбор диагностики

<a id="version"></a>

### Версия

Ни одного выпуска ещё не опубликовано, поэтому номер версии не позволяет различить сборки. Всё
собирается из исходного кода, так что указывайте коммит, из которого вы собирали:
`git rev-parse --short HEAD` в вашей рабочей копии. У CLI нет флага версии, а
`capsule-server --version` выводит только версию крейта, одинаковую для всех сборок.

<a id="logs"></a>

### Логи

CLI и сервер пишут логи в **stderr**. В stdout попадает только то, что выводит команда, а с
`--json` это единственный JSON-документ, поэтому их можно сохранить по отдельности:

```sh
RUST_LOG=debug capsule push --library ~/Photos.capsule 2> capsule.log
```

- `RUST_LOG` задаёт подробность логов. Релизная сборка по умолчанию пишет на уровне `info`,
  отладочная — на уровне `debug`. Используйте `RUST_LOG=debug`, когда воспроизводите проблему,
  и `RUST_LOG=trace` только по просьбе: этот лог очень большой.
- Формат логов сервера задаётся `LOG_FORMAT`: по умолчанию `pretty` в отладочных сборках и
  `json` в релизных ([](/development/local-development/#logs)).
- Полноэкранный TUI (просто `capsule` в терминале) не может писать логи на экран, который сам
  рисует, поэтому он пишет `tui.log` в каталог кеша CLI — `capsule status` выводит его как Cache
  Directory. Файл перезаписывается в каждом сеансе, поэтому скопируйте его, прежде чем снова
  запускать TUI.
- Вывод `--json` — самая точная запись того, что сделала команда, потому что он сообщает
  результат по каждому объекту. Прикладывайте его, когда команда сообщает о сбоях.

**Удалите лишнее, прежде чем делиться.** Уберите парольные фразы, секреты восстановления,
токены, ключи, адреса серверов и личные пути к файлам. Никогда никуда не вставляйте парольную
фразу библиотеки или секрет восстановления, даже в закрытый отчёт.

<a id="the-server"></a>

## Сервер

<a id="it-refuses-to-start"></a>

### Он не запускается

- **Код выхода 2 с перечислением переменных.** Надёжному серверу нужны `DATABASE_URL`,
  `BLOB_ROOT`, `JWT_ED25519_DER` и `ATTESTATION_KEY_SEED`, и он сразу называет все
  отсутствующие. См. [](/guides/self-hosting/#configure).
- **Схема базы данных старше бинарного файла.** `serve` никогда не выполняет миграции.
  Запускайте `capsule-server-migration up` при каждом обновлении, до `serve`
  ([](/guides/self-hosting/#migrate-then-start)).
- **Отклоняется настройка доверенного прокси.** `TRUSTED_PROXIES` отклоняет сеть `/0`, а
  `TRUSTED_PROXY_HEADER` принимает только `x-forwarded-for` или `forwarded`.

Работающий сервер выводит в stdout `listening on <url>`.

<a id="clients-cant-sign-in-or-connect"></a>

### Клиенты не могут войти или подключиться

- `capsule server-info` показывает, как сервер выполняет вход: есть ли у него поставщик
  удостоверений и отклоняет ли он пароли. Вход по паролю на сервер с отключёнными паролями
  не удаётся — так задумано.
- За обратным прокси все клиенты делят ограничение частоты запросов прокси, пока прокси не
  указан в `TRUSTED_PROXIES` или `TRUSTED_PROXY_HOPS`. Если ограничение срабатывает сразу у
  нескольких людей, проверьте это в первую очередь ([](/guides/self-hosting/#configure)).

<a id="the-index-and-the-blob-store-disagree"></a>

### Индекс и хранилище блобов расходятся

`capsule-server scrub` — проверка целостности только для чтения; при любой находке она
завершается с ненулевым кодом. После восстановления из резервной копии или потери базы данных
`capsule-server rebuild` сравнивает индекс с журналами владельцев. Она ничего не меняет, пока вы
не остановите `serve` и не запустите `capsule-server rebuild --apply`
([](/guides/self-hosting/#maintenance)).

<a id="imports-and-uploads"></a>

## Импорт и загрузка

- **`push` остановился на полпути.** Запустите его снова. Загрузка продолжается с места
  остановки, поэтому повторный запуск всегда безопасен. `push` завершается с ненулевым кодом,
  если хотя бы один объект не загрузился, а `--json` выводит результат по каждому объекту
  ([](/guides/user-guide/#import-and-back-up)).
- **Храните оригиналы, пока хранение не подтверждено.** Не удаляйте исходный файл, пока `push`
  не отметит его объект как проверенный, или используйте `import --move --push`, который
  удаляет каждый исходный файл только после проверки его объекта.
- **Экспорт из Google Photos выглядит неполным.** Убедитесь, что все части экспорта Takeout
  скачаны и распакованы, и прочитайте, чего импортёр не может гарантировать
  ([](/guides/google-photos-migration/#what-the-importer-cannot-guarantee)).
- **Неверное время съёмки.** `capsule repair capture-time` сообщает о каждом объекте, у
  которого подписанное время съёмки расходится с EXIF оригинала, а `--apply` исправляет их.
  Каждое исправление — постоянная подписанная запись, поэтому сначала запустите команду без
  `--apply`.

<a id="check-a-librarys-integrity"></a>

## Проверка целостности библиотеки

Если фотографии кажутся пропавшими или повреждёнными, **остановитесь и ничего не удаляйте**,
пока разбираетесь: удаление может уничтожить контекст, нужный для восстановления.

1. `capsule verify --library <path>` спрашивает сервер, надёжно ли он хранит каждый оригинал.
   `--deep` заставляет сервер заново вычислить хеш сохранённых байтов, а не только проверить их
   наличие, а `--signed` сохраняет в библиотеке подписанный вердикт сервера.
2. Объекты в корзине можно восстановить в течение их периода хранения:
   `capsule trash restore --library <path> --asset <id>` возвращает объект
   ([](/guides/user-guide/#delete-safely)).
3. Для потерянного устройства или ключа есть отдельные процедуры:
   [](/design/backup-recovery/#recovery-paths).

Если данные потеряны или повреждены, сообщите об этом как об ошибке и приложите вывод каждого
шага. Потеря или повреждение данных — это дефект, какой бы ни была причина.
