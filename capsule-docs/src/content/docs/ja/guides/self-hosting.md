まだリリースは公開されていないため、サーバーはソースからビルドします。サーバーが保存するのは暗号文だけで、メディアをデコードすることはありません。処理と暗号化はすべてクライアントが行います。

<a id="what-you-need"></a>

## 必要なもの

- **PostgreSQL 18**：永続的なインデックス（アカウント、アセット、クォータ）と、サーバーの有効期限付きの状態（サインインセッション、アップロードセッション、レートカウンター）を保持します。サーバーが使う唯一のデータベースであり、耐久性に関する設定を損なわずに運用しなければなりません（[](#postgresql)）。
- **blobディレクトリ**（`BLOB_ROOT`）：`fsync`を守り、ファイルロックを共有する**単一のPOSIXファイルシステム**上に置きます。blobと、`ledger/`の下に各所有者の署名付き台帳を保持し、インデックスはこの台帳から再構築できます（[](#blobディレクトリ)）。
- **TLSを終端するリバースプロキシ**：サーバーの前段に置き、圧縮には手を加えずにそのまま通します（[](#リバースプロキシ)）。
- **同期された時計**：ホストの時刻をNTPで合わせておきます（[](#時計)）。

### PostgreSQL

サーバーは行がコミットされた時点で書き込みに応答します。そのため、PostgreSQLがコミットを確認した後にそれを失うと、取り消したはずのセッションが復活したり、第2要素のコードが2回受け付けられたりする可能性があります。次の状態を保ってください。

- `fsync = on`と`full_page_writes = on`（デフォルト）。
- `synchronous_commit`を`on`、`local`、`remote_write`、`remote_apply`のいずれかにし、決して`off`にしない。
- データディレクトリを、フラッシュを確実に実行するストレージに置く。停電保護のないディスクの書き込みキャッシュや、ホストがフラッシュを無視する仮想ディスクでは、停電時に確認済みのコミットが失われます（[](/design/filesystem/server/)）。

PostgreSQLは、`BLOB_ROOT`とは別のファイルシステム、ディスク、ホストに置いてもかまいません。

<a id="blob-directory"></a>

### blobディレクトリ

`BLOB_ROOT`はファイルシステムとの契約であり（[](/design/filesystem/server/#blob-root-filesystem-contract)）、そのレイアウトは[](/design/filesystem/server/#blob-store-layout)のとおりです。

- **単一のファイルシステム**。確定処理はアトミックなリネームで行われるため、`incoming/`を含むツリー全体が、複数のボリューム、データセット、Kubernetes PersistentVolumeにまたがってはいけません。
- **`fsync`が守られること**。サーバーが書き込みを確認する前に、ファイルとディレクトリの両方で`fsync`が実際に行われる必要があります。
- **ファイルロックが共有されること**。ツリーに書き込むすべてのプロセスでファイルロックが共有される必要があります。`serve`と`purge --apply`は、追記する前に各所有者の`ledger/<owner>/.lock`をロックします（[](/design/filesystem/server/#concurrent-appenders)）。
- **blobディレクトリ1つにつき`serve`は1つ**。アップロードのチャンクと確定処理はサービス中のプロセス内で確保されるため（[](/design/transfer/upload/)）、1つのツリーに対して2つの`serve`プロセスを動かす構成は、同じホスト上でも別々のホスト上でもサポートされません。`gc`、`purge`、`scrub`は並行して実行できますが、`rebuild --apply`は`serve`を停止してから実行する必要があります（[](#メンテナンス)）。

サポート対象：

- ローカルストレージまたはブロックストレージ上のext4、XFS、btrfs（ディスク、RAID、LVM、iSCSI、クラウドのブロックボリューム）。
- `sync=standard`（デフォルト）または`sync=always`のZFS。
- `sync`でエクスポートされたNFSv4、またはロックマネージャー付きのNFSv3。
- 上記のいずれかを基盤とするKubernetes PersistentVolumeまたはコンテナボリューム。

サポート対象外：

- 書き込みバリアを無効にしたマウント、またはホストがフラッシュを無視する仮想ディスク。
- `sync=disabled`のZFS。書き込まずに`fsync`を確認してしまいます。
- `async`でエクスポートされたNFS（NFSサーバーがまだ保存していない書き込みを確認してしまいます）、または`nolock`、`local_lock=flock`、`local_lock=all`でマウントされたNFS（ロックが1台のホスト内に限定されます）。
- SMB/CIFS共有。
- FUSEファイルシステム（sshfs、rclone mount、s3fs、gcsfuse）と、あらゆるオブジェクトストレージのマウント。
- 1つのツリーを複数のディスクに分散させるプーリングやユニオンファイルシステム（mergerfs、`/mnt/user`以下のUnraidユーザー共有）。メンバーディスク間のリネームはコピーであり、アトミックなリネームではありません。
- コンテナ自身の書き込み可能レイヤー、およびコンテナ用VMにバインドマウントしたmacOSやWindowsのホストディレクトリ。VM内のボリュームを使ってください。

Linuxでは、NFS上の`flock`はバイト範囲ロックでエミュレートされ、ロックマネージャーがそれをホスト間で共有します。ロックを無効にすると、別々のホストで動く`serve`と`purge --apply`が、台帳への追記を交互に混在させてしまう可能性があります。

- **ハードウェアを信頼する前に、停電テストを行ってください**。`serve`は起動時にファイルシステムの種類、アトミックなリネーム、ロックの共有を確認しますが、実際には行っていないフラッシュを完了したと報告するディスク、コントローラー、ハイパーバイザーは、どんなソフトウェアのチェックでも見抜けません。実際に運用するハードウェアで、アップロード中に電源を落とし（正常なシャットダウンではなく）、起動してから`capsule-server scrub --deep`を実行してください。サーバーが確認したすべてのアップロードが無傷でなければなりません（[](/design/filesystem/server/#blob-root-filesystem-contract)）。
- **空き容量を残してください**。blobルートは空き容量の予備を確保します。デフォルトはボリュームの2%と4 GiBのうち大きい方です。これを下回ると、新しいアップロードは`507`で拒否されますが、すでにサーバー上で進行中のアップロードは完了し、削除も引き続き機能します（[](/design/quota/#enforcement-points)）。この予備は計画中で、まだ実装されていません。実装されるまでは、ディスクが満杯になるとすべての書き込みが拒否されます。
- **隔離領域は意図して整理してください**。`quarantine/`には、ハッシュの再計算に失敗したblobや読み取れなかったblobが、削除するまで保持されます（その後修復されたものを除く）。計画中の`capsule-server quarantine prune`は、削除する前に一覧を表示し、`--apply`なしでは何も削除しません（[](/design/filesystem/server/#quarantine-retention)）。`scrub`が隔離領域のサイズを報告するので、そこで監視してください。

<a id="reverse-proxy"></a>

### リバースプロキシ

TLSはプロキシで終端し、サーバーでは決して終端しません（[](/design/networking/#transport-security)）。サーバーは平文のHTTPで待ち受け、プロキシからのみ到達できるようにしなければなりません。ループバック、プライベートネットワーク、Podネットワークのいずれかを使います。プロキシは次のように設定してください。

- 最大のアップロードチャンクである16 MiB以上のリクエストボディを受け付ける。
- リクエストボディをバッファリングせず、サーバーにストリーミングする。
- TLSのアーリーデータ（0-RTT）を無効にするか、サーバーが書き込みを拒否できるよう`Early-Data: 1`ヘッダーを付けて転送する。
- リクエストボディに合計時間のタイムアウトを設けず、アイドルタイムアウトはサーバーのストール上限より長くする。そうすれば、遅くても着実に届いているチャンクが切断されることはありません。
- **圧縮には手を加えずにそのまま通す**。どのレスポンスを圧縮するかはサーバーが決め、`application/octet-stream`は決して圧縮しません（[](/design/networking/#compression)）。プロキシは、Capsuleのアップストリームのレスポンスをサーバーが送ったとおりに通します。レスポンスをgzipなどで圧縮してはならず（MUST NOT）、解凍したり`Content-Encoding`を追加・変更・削除したりしてもならず（MUST NOT）、クライアントの`Accept-Encoding`を変更せずに転送しなければなりません（MUST）。nginxでは、Capsuleのサイトに`gzip off;`を設定したままにしてください。これにより、ディストリビューションの`nginx.conf`から継承した`gzip on;`が上書きされます。Caddyでは`encode`ディレクティブを追加せず、Traefikでは`compress`ミドルウェアを付けないでください。

プロキシのクライアント側でのHTTP/2とHTTP/3は任意です。クライアントはHTTP/1.1にフォールバックします。カーネルTLS（kTLS）やNICへのTLSオフロードを使いたい場合は、プロキシ側の設定になります（nginxでは`ssl_conf_command Options KTLS;`と`sendfile on;`）。サーバー自身のTLSスタックは、サーバーから開始する接続、つまりOpenID Connectプロバイダーとフェデレーションのピアへの接続にのみ使われます。これらの接続が信頼するのは、同梱のMozillaルート証明書と`OIDC_CA_BUNDLE`で指定したものであり、ホストの証明書ストアではありません。

<a id="clock"></a>

### 時計

サーバーは自身の時計で時刻を判断し、いくつかのルールはその時計が正しいことを前提にしています。ホスト上でNTP（chronyまたはsystemd-timesyncd）を使って同期を保ってください。コンテナはホストの時計を読むので、同期すべきなのはホストです。ずれは1秒以内に保つべきであり（SHOULD）、30秒以内に保たなければなりません（MUST）。この範囲を超えると次のような問題が起きます。

| ずれ | 起きる問題 |
| --- | --- |
| 30秒超 | 第2要素のコードが通らなくなり始めます。コードはサーバーの時計で30秒のステップ1つ分の範囲内でしか受け付けられません（[](/design/authentication/)） |
| 5分超 | フェデレーションが双方向で止まります。ピアはこのサーバーの署名付きリクエスト、ヒント、レポートを拒否し、このサーバーもピアのものを拒否します（[](/design/federation/)） |
| 時計が進んでいる | ゴミ箱の中身が保持期間の終了前に完全に削除され、期限内に行った復元も拒否されます（[](/design/organization/#retention-window)）。セッション、共有リンク、アップロードセッションが早く期限切れになります |
| 時計が遅れている | 期限切れのセッション、共有リンク、カウンターが、設定より長く有効なままになります |
| 大幅なずれ | クライアントは、`received_at`が不自然な保管受領証を拒否します（[](/design/transfer/durability/)） |

`serve`は、時計が同期されてから起動してください。systemdでは、`chrony-wait.service`または`systemd-time-wait-sync.service`を有効にしたうえで、`time-sync.target`の後に起動するよう順序付けします。スナップショットから復元した仮想マシンは、スナップショット時点の時計のまま再開します。`serve`が起動する前に、NTPで時刻を補正させてください。サーバーはまだ、時計のずれを自分で検出したり報告したりしません。

<a id="hardware"></a>

## ハードウェア

以下の数値は、サーバーとPostgreSQLを1台のノードでまとめて動かす場合のものです。ベンチマークではなく、サーバーの処理内容から導いたサイジングの目安です。

サーバーの処理は軽いため、ハードウェア予算の大半は**ストレージ**に充てるべきです。サーバーは各チャンクの到着時にSHA-256でハッシュを計算し、確定処理時と`scrub --deep`の実行中にもう一度ハッシュを計算します。確定処理時にはクライアントのハイブリッド署名（Ed25519とML-DSA-65）を検証し、受領証も同じ方式で署名します。また、パスワードでのログインごとにArgon2idを1回実行します（1回あたり約19 MiB）。メディアのデコード、リサイズ、トランスコードは一切行わず、暗号化も復号もせず、TLSはリバースプロキシに任せます。アップロードのボディは1チャンクを超えてバッファリングされないため、メモリ使用量はファイルサイズに応じて増えません。

| | 最小 | 推奨 |
| --- | --- | --- |
| **CPU** | 2コア、x86_64またはarm64 | 4コア。SHA-2命令（x86_64のSHA-NI、Armv8の暗号拡張）があるとハッシュ計算が速くなります |
| **RAM** | 2 GB | 4～8 GB。大きなライブラリではPostgreSQLのキャッシュに役立ちますが、先に効果が出るのはストレージへの投資です |
| **システムストレージ** | SSD、空き10 GB | PostgreSQL用にSSDまたはNVMe |
| **blobストレージ** | ライブラリのサイズに、転送中のアップロード分を加えた容量 | 冗長化したディスク（ミラー、RAID、ZFS）を、数年分の増加を見込んだ容量で。HDDで問題ありません |
| **ネットワーク** | 上り10 Mbit/s | LAN内はギガビット。外部からデバイスが同期する場合は上り50 Mbit/s以上 |
| **電源** | — | 停電でPostgreSQLの書き込みが途中で途切れないよう、UPSを用意 |

- **`BLOB_ROOT`は1つのファイルシステムに収めてください**。`incoming/`を含むツリー全体が1つのファイルシステムでなければならないため、SSDとディスクアレイに分けたり、2つのZFSデータセットに分けたりすることはできません。すべてをアレイに置いてください。
- **サーバーが使わないメモリはPostgreSQLに回してください**。認証済みのリクエストはすべてPostgreSQLからセッションを読み込み、アップロードのチャンクはすべてそこに範囲を記録します。そのため、PostgreSQLのキャッシュはライブラリのインデックスだけでなく、リクエストの処理経路にも効きます。セッション、アップロードセッション、カウンターは小さく、期限切れになるとサーバーが削除します。
- **リモートのデバイスにとっては上りの帯域が上限になります**。自宅のネットワークの外にあるスマートフォンは、こちらの回線の*下り*速度でアップロードしますが、プレビューやオリジナルを取得するたびに、データはこちらの*上り*速度で出ていきます。チャンクが切断されるのは到着が止まったときだけで、時間がかかったという理由で切断されることはありません。クライアントは計測した速度に応じて、短い目標時間内に終わるようチャンクのサイズを決めるため、遅い回線でもその回線なりの速度でアップロードされます。サーバーのストール上限はプロキシのアイドルタイムアウトより短くしてください。そうすれば、プロキシが切断する前にサーバーがストールしたチャンクに応答します。
- **ディスク容量は派生ファイルではなくオリジナルを基準に見積もってください**。RAWファイルと動画のライブラリでは、派生ファイルが占める割合はわずかです。サーバーは各blobを、クライアントが暗号化したままの形で1つだけ保持します。
- **ユーザーが増えて増えるのは帯域であり、計算量ではありません**。検索、サムネイル、整理はクライアントで実行されます。閲覧する人が増えれば配信するバイト数は増えますが、CPUやRAMはほとんど増えません。

`capsule-server/compose.yaml`は、ローカル利用向けの適切な設定でPostgresを起動します（`mise run serve-deps`）。その認証情報は開発専用です。

<a id="build"></a>

## ビルド

```sh
cargo build --release -p capsule-server -p capsule-server-migration
```

バイナリはglibcにリンクされており、ほかに何もインストールする必要はありません。書き込み可能なパスが`BLOB_ROOT`だけである非特権ユーザーで実行してください。これは後述のコンテナイメージが強制する構成と同じです。

<a id="container-image"></a>

## コンテナイメージ

:::caution
イメージはまだ公開されておらず、`/livez`と`/readyz`のルートや`healthcheck`サブコマンドもまだ実装されていません。このセクションは、イメージが準拠して作られる契約です。
:::

- **ベース**：`gcr.io/distroless/cc-debian12:nonroot`を、ダイジェストで固定して使います。glibc、GCCランタイム、CA証明書、タイムゾーンデータを含み、シェルやパッケージマネージャーは含みません。
- **アーキテクチャ**：`linux/amd64`と`linux/arm64`向けの1つのマルチアーキテクチャイメージで、それぞれのglibcターゲット向けにネイティブにビルドされます。特定のCPU向けのチューニングは行わず、ハッシュ計算では実行時にSHA-NIまたはArmv8の暗号拡張が選ばれます。
- **内容**：同じビルドから生成された`capsule-server`（エントリーポイント、デフォルトは`serve`）と`capsule-server-migration`。
- **ユーザー**：非root、UIDとGIDは65532。コンテナはLinuxケーパビリティを一切必要としないので、すべて削除し、`no-new-privileges`を設定してください。
- **読み取り専用のルートファイルシステム**。サーバーが書き込むのは`BLOB_ROOT`の下だけなので、blobディレクトリをUID 65532が所有する唯一の書き込み可能ボリュームとしてマウントし、ルートは読み取り専用でマウントしてください。
- **リスナー**：コンテナ内では`SERVER_HOST=0.0.0.0`（または`::`）を設定します。デフォルトのポートは3000です。公開先はリバースプロキシだけにしてください（[](#リバースプロキシ)）。
- **ログ**はstderrに出力されます。ログコレクターを使う場合は`LOG_FORMAT=json`を設定してください。
- **停止**：`serve`は`SIGTERM`を受け取ると正常にシャットダウンします。停止によって中断されたアップロードは、サーバーがコミット済みの範囲から再開されます。
- **レプリカは1つ**。blobディレクトリ1つにつき、`serve`はちょうど1つだけ実行してください（[](#blobディレクトリ)）。Kubernetesでは、レプリカを1つにし、更新戦略を`Recreate`にしてください。ローリングアップデートでは、古いサーバーがまだサービスしている間に新しいサーバーが起動してしまいます。
- **マイグレーション**は、`serve`の起動前に同じイメージタグから、Job、initコンテナ、または`ExecStartPre=`として実行します：`capsule-server-migration up`（[](#マイグレーションしてから起動する)）。
- **メンテナンス**コマンドは、同じイメージから、同じユーザーで、同じボリュームに対して、CronJobやタイマーとして実行します（[](#メンテナンス)）。
- **ヘルスチェック**：`/livez`はプロセスがサービスしている間`GET`に応答し、それ以外は何も確認しません。livenessプローブ用です。`/readyz`は、PostgreSQLが応答し、スキーマがバイナリと一致し、`BLOB_ROOT`が書き込み可能な間だけ応答します。readinessプローブ用です。どちらも`/v1`の外にあるため、プローブがプロトコルのバージョンに依存することはなく、プロキシ経由で到達できる必要もありません。イメージには`curl`が含まれていないため、イメージ自身のヘルスチェックは`capsule-server healthcheck`を実行し、これがローカルのリスナーの`/livez`を呼び出します。
- **時計**：コンテナはホストの時計を読むので、ホストを同期してください（[](#時計)）。

<a id="configure"></a>

## 設定

設定は環境変数のみで行います。`capsule-server/.env.example`がひな形で、このページでは運用者が決めなければならない変数を取り上げます。次の変数がないと、永続化されたサーバーは起動を拒否し（終了コード2）、足りない変数をすべて一度に表示します。

| 変数 | 用途 |
| --- | --- |
| `DATABASE_URL` | PostgreSQLへの接続 |
| `BLOB_ROOT` | blobディレクトリ |
| `JWT_ED25519_DER` | セッショントークンに署名する、Base64形式のEd25519鍵 |
| `ATTESTATION_KEY_SEED` | 保管受領証に署名する、Base64形式のシード。トークン鍵とは独立していなければなりません |

- **何よりもトークン鍵を守ってください**。データベースにはベアラーシークレットが一切保存されていないため、データベースやバックアップが漏洩しても、それだけではセッションは得られません。その漏洩をすべての有効なセッションの漏洩に変えてしまうのが`JWT_ED25519_DER`です（[](/design/authentication/#session-token)）。リフレッシュトークンの再利用検出（[](/design/authentication/#token-lineage-and-reuse)）はこれに対しては役に立ちません。鍵を持つ者はトークンを再送するのではなく、トークンを新たに発行できるからです。鍵はシークレットストアに保管し、データベースやそのバックアップには決して置かないでください。漏洩が疑われる場合はローテーションしてください。これにより、すべてのデバイスがサインアウトされます。
- **第2要素の封印鍵を計画しています**。サーバーは、トークン鍵とは独立した専用の鍵で、保存時のTOTPシークレットを封印する予定です。そうすれば、データベースやバックアップが漏洩しても第2要素は漏れず、トークン鍵をローテーションしても第2要素が使えなくなることはありません（[](/design/authentication/#the-second-factor)）。この設定はまだ存在しません。導入されたら、トークン鍵と同様に、データベースやそのバックアップとは分けて保管してください。
- **オープン登録にはデフォルトのクォータが必要です**（予定）。クォータを設定できるようになると、パスワードでの登録が有効でデフォルトの上限がない場合、`serve`は起動を拒否します。上限を設けたくない運用者は、明示的に`unlimited`を設定する必要があり、これは起動のたびに`WARN`でログに記録されます（[](/design/quota/#thresholds-and-states)）。現時点では、すべてのデプロイが無制限で動作しています。

`SYNC_CURSOR_MAC_KEY`は、未設定の場合`JWT_ED25519_DER`から導出されます。そのため、明示的に設定しない限り、トークン鍵をローテーションすると未使用の同期カーソルも無効になります。フェデレーションは、`FEDERATION_ENABLED=true`と`FEDERATION_URL`を設定しない限り無効です。無効のままにしておいてください。

送信元ごとのレート制限がプロキシではなくクライアントを見られるよう、リバースプロキシを指定してください。

| 変数 | 意味 |
| --- | --- |
| `TRUSTED_PROXIES` | カンマ区切りのアドレスとCIDRネットワーク（`10.0.0.0/8`）。`/0`のネットワークは、すべての送信者を信じることになるため拒否されます。 |
| `TRUSTED_PROXY_HOPS` | サーバーに最も近い、指定した数の転送ホップを、アドレスにかかわらず信頼します。 |
| `TRUSTED_PROXY_HEADER` | サーバーが読み取る唯一の転送フィールド：`x-forwarded-for`（デフォルト）または`forwarded`（RFC 7239）。それ以外の値では起動を拒否します。 |

未設定の場合、転送ヘッダーは一切信用されません。これは安全ですが、プロキシの背後にいるすべてのクライアントがプロキシの枠を共有することになり、パスワードを推測しようとする見知らぬ1人のせいで全員のサインインが遅くなります（[](/design/authentication/#sign-in-limits)）。ホップを1つも信頼していない状態で転送ヘッダーを受け取ると、サーバーは警告をログに出力します。逆の間違いのほうが深刻です。クライアントのアドレスを追記しないホップを信頼すると、どのクライアントも自分のレート制限キーを自由に選べてしまいます。`TRUSTED_PROXY_HEADER`で指定していないフィールドは、誰が送ってきても無視されます。そのため、プロキシがそのまま通すフィールドをクライアントが送っても、自分のレート制限キーを選ぶことはできません。プロキシが追記するフィールドを指定してください。デフォルトのままなら、プロキシが受け取ったアドレスを`X-Forwarded-For`に追記するようにしてください。nginxでは次のように設定します。

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

`TRUSTED_PROXY_HEADER=forwarded`は、プロキシが`Forwarded`に自身の要素を追記し、かつ`X-Forwarded-For`を書き込まない場合にのみ設定してください。

<a id="migrate-then-start"></a>

## マイグレーションしてから起動する

`serve`はマイグレーションを行わず、バイナリより古いデータベーススキーマを拒否します。アップグレードのたびに、先にマイグレーションを実行してください。

```sh
DATABASE_URL=… capsule-server-migration up
capsule-server serve
```

`serve`はstderrにログを出力し、stdoutに`listening on <url>`を出力します。本番環境では`--memory`を使わないでください。blob以外のすべてをプロセスのメモリ上に保持してしまいます。

<a id="maintenance"></a>

## メンテナンス

次の単発コマンドをスケジュール実行してください（cronまたはタイマー）。これらには`DATABASE_URL`と`--blob-root`が必要で、デフォルトではドライランとして動作します。

- `capsule-server gc --apply`：猶予期間を過ぎた参照されていないblobを回収し、期限切れのセッション、アップロードセッション、カウンターを削除します。ストレージに余裕があっても定期的に実行してください。
- `capsule-server purge --apply`：保持期間が過ぎたソフト削除済みのアセットを完全に削除します。各削除は先に所有者台帳（[](/design/filesystem/server/#the-owner-ledger)）に署名付きで記録されるため、サーバーの`ATTESTATION_KEY_SEED`も必要で、これがないと実行を拒否します。台帳に削除を記録できなかった場合は0以外の終了コードで終了し、そのアセットは次回の実行まで残されます。
- `capsule-server scrub [--deep]`：インデックスとblobストアの読み取り専用の整合性チェックです。**何か見つかると0以外の終了コードで終了する**ので、それをアラートの条件にしてください（[](/design/filesystem/maintenance/#server-side-integrity-scrub)）。

バックアップを復元した後やデータベースを失った後は、`BLOB_ROOT`の下にある所有者台帳からインデックスを再構築します（[](/design/filesystem/server/#rebuild)）。台帳の署名を検証できるよう、ホストに`ATTESTATION_KEY_SEED`を設定してください。

1. `capsule-server rebuild`は、インデックスを台帳と比較します。
2. `serve`を停止した状態で、`capsule-server rebuild --apply`は、インデックスに欠けている行を復元します。インデックスにすでにある行を上書きすることはありません。末尾が失われた台帳はアンカーを付け直し、その後サーバーはその所有者への書き込みを再開します。
3. 台帳が書き換えられていたとレポートに表示された場合、調査したうえで`capsule-server rebuild --apply --accept-rewrites`を実行するまで、サーバーはその所有者の書き込みを拒否します。

blobのサイズを記録するようになる前にライフサイクル操作（削除、復元、メタデータの更新、派生ファイル、置き換え）を適用したサーバーでは、それらの参照がサイズ0のまま保持されています。`capsule-server repair-sizes`を一度実行して一覧を表示し、続いて`capsule-server repair-sizes --apply`を実行すると、blobストアから各サイズが補完されます。
これは`serve`の稼働中に実行しても安全で、修復された各アセットはクライアントに再送されます。blobが見つからないか空の場合は0以外の終了コードで終了し、その参照は元のまま残します。

<a id="backups"></a>

## バックアップ

永続的な状態は、PostgreSQLと`BLOB_ROOT`（blobと`ledger/`）です。両方をまとめてバックアップしてください。データベースにはサインインセッションと転送中のアップロードセッションも保存されているため、復元してもユーザーはサインインしたままになります。上記の鍵の変数もシークレットストアに保管してください。これらはデータベースには含まれておらず、サーバーの署名とアテステーションのアイデンティティはこれらに依存しています。

データベースを先に、blobを後に取得します。

```sh
pg_dump --format=custom --file=capsule.dump "$DATABASE_URL"
rsync -a "$BLOB_ROOT"/ backup/blob-root/
```

`serve`は動かしたままでかまいません。blobはディスクに書き込まれ、台帳のエントリが追記されてから、それを参照するインデックスの行がコミットされます。そのため、ダンプの後に取得したblobのコピーには、ダンプが参照するすべてのblobが含まれ、ダンプが取りこぼした書き込みも含まれる可能性があります。バックアップの実行中は`gc --apply`や`purge --apply`を実行しないでください。どちらも、ダンプがまだ参照しているblobを削除してしまう可能性があります。

後述の再構築は、ダンプとblobのコピーの間にアップロードされたアセットを復元します。インデックスに欠けているすべての行を追加するからです。ダンプにすでにある行は変更しないため、その間に古いアセットに対して行われた削除、復元、メタデータの編集は反映されません。再構築がそのような変更を差分のある行として報告する（そして0以外の終了コードで終了する）のは、その変更がアセットのblobを変えた場合だけで、削除や復元は報告されません。バックアップですべての変更を確実に捕捉する必要がある場合は、両方を取得する間`serve`を停止してください。復元時に差分のある行が報告され、古いホストがまだ動いている場合は、その方法でバックアップを取り直してください。

<a id="restoring-onto-a-new-host"></a>

### 新しいホストへの復元

1. 空のPostgreSQLを起動し、古いホストと同じ`JWT_ED25519_DER`と`ATTESTATION_KEY_SEED`を設定します。
2. データベースを復元します。ダンプにはスキーマとそのマイグレーション記録が含まれているため、先に`capsule-server-migration up`を実行しないでください：
   `pg_restore --no-owner --exit-on-error --dbname "$DATABASE_URL" capsule.dump`。
3. blobディレクトリを、1つのファイルシステム上の`BLOB_ROOT`にコピーして戻します。
4. `serve`を停止した状態で`capsule-server rebuild`を実行し、レポートを読みます。レポートにはダンプ後にアップロードされたアセットが一覧表示されます。`capsule-server rebuild --apply`はそれらを元のシーケンス番号のまま復元するため、クライアントの同期カーソルは有効なままです。
5. `capsule-server scrub --deep`を実行します。何も報告されないはずで、何か見つかった場合は0以外の終了コードで終了します。
6. `serve`を起動します。セッションはデータベースとともに戻るため、ダンプ時点でサインインしていたクライアントは、その後セッションが期限切れになっていない限りサインインしたままです。待ち受けを始める前に、`serve`は`BLOB_ROOT`の下にあるステージングファイルが復元されなかった未完了のアップロードセッションをすべて破棄し、セッションのないステージングファイルをすべて削除します。アップロードが破棄されたクライアントは、そのファイルを最初からアップロードし直します。クライアントは中断したところから同期を再開します。

データベースを失い、ダンプもない場合は、空のデータベースをマイグレーションし、blobディレクトリに対して`capsule-server rebuild --apply`を実行します。所有者台帳から、すべてのアセットの行が復元されます。アカウント、公開済みのデバイスディレクトリ、アルバムのメンバー、共有リンクはデータベースにしかなく、再構築では復元されません。

実際のデータを任せる前に、この手順をリハーサルしてください。たとえば、すべてのオリジナルがバイト単位で正確に戻ってくることを`capsule restore`で確認します。`capsule-e2e/tests/backup_restore_drill.rs`は、同じ手順をコンテナに対して実行します（`mise run test-rust-containers`）。
